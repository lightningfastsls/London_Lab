# LMT integration code belongs in dedicated src-usv_spectrogram-lmt subpackage

The Live Mouse Tracker integration code should live in its own subpackage at `src/usv_spectrogram/lmt/` rather than being distributed across existing modules like `detection/` or a future `analysis/` package. This is an architectural boundary decision driven by dependency isolation and data model separation.

LMT data comes from a fundamentally different source than the rest of the pipeline. Where the core codebase operates on WAV files (300 kHz audio, processed through STFT and energy detection), LMT data comes from SQLite databases generated by video-based behavioral tracking. The data model is frame-by-frame animal positions and annotated behavioral events (approach, contact, follow, mount, etc.) — structurally nothing like spectrograms or detection candidates. Mixing LMT code into existing modules would create coupling between two independent data domains and force LMT's SQLite dependency onto code that has no use for it.

The subpackage structure follows the data flow from raw behavioral data to integrated analysis:

1. **db_loader.py** — reads LMT SQLite databases and produces structured Python objects representing behavioral events, animal positions, and session metadata. This is the single point of contact with the SQLite schema, isolating schema-version dependencies.
2. **synchronizer.py** — aligns LMT timestamps (video frame indices at ~30 fps) with WAV file timestamps (sample indices at 300 kHz). This is the bridge module that translates between behavioral and acoustic time domains. Whether synchronization metadata exists in the SQLite DB (via AviSoft integration) or must be constructed from recording start times determines the complexity here.
3. **event_triggered.py** — computes peri-event time histograms (PETH) and event-triggered averages. Given a set of behavioral events and a set of USV detections, this module answers questions like "what is the USV rate in the 2 seconds surrounding a mount attempt?"
4. **context_analysis.py** — the highest-level module, combining behavioral context with vocal repertoire analysis. This is where questions like "do USV code distributions differ between approach vs. contact contexts?" get answered.

This separation means the rest of the codebase — detection, spectrogram generation, transformer training, VQ-VAE — can be developed, tested, and deployed without any LMT dependency. Conversely, LMT code can be developed against mock data before real SQLite files are available, since [[pre-code questions for LMT integration must be resolved before implementation]].
