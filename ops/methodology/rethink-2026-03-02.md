## Pattern Analysis

### Pattern A: "Automation gaps in the pipeline lifecycle"

**Evidence:** Observations #4 (stale docs), #7 (/reduce weak descriptions), #8 (ghost inbox items)

**What connects them:** Each describes a step in the knowledge pipeline where automation handles the primary task but misses a lifecycle bookkeeping step. /reduce extracts notes but doesn't archive the source. /seed marks status but doesn't move files. Documentation stays current only when manually updated. The pattern is: **primary task automation is solid, but lifecycle transitions between stages are manual and get dropped.**

**Root cause:** The pipeline was designed as a sequence of independent skills (/seed, /reduce, /reflect, /reweave), each focusing on its core operation. The handoff points between stages (source archival, doc updates, description quality review) were left implicit.

### Pattern B: "Self-review bias in the implementation loop"

**Evidence:** Observation #1 (master-reviewer bias), Tension #8 (sycophancy as product decision), Tension #7 (contract comprehensiveness)

**What connects them:** All three concern the reliability of self-monitoring systems. The master-reviewer catches bugs but the implementor interprets and approves its own fixes. Sycophancy means models drift toward confirming rather than challenging. And comprehensive contracts that attempt to prevent this drift degrade the very instruction-following capacity they depend on. The pattern is: **self-monitoring degrades proportionally to the complexity of what's being monitored.**

**Root cause:** The agent is both implementor and quality gatekeeper. Structural separation (different chat sessions, fresh context) is the only reliable intervention.

### Pattern C: "Topic map sprawl from bulk ingestion"

**Evidence:** Topic map note counts (classification: 87, experimental-methods: 68, detection: 54, agent-governance: 54, representation-learning: 49 -- all above the 40-note threshold). Last session already split representation-learning from 113 notes into 4 maps.

**What connects them:** Rapid bulk ingestion (8 /learn sessions depositing ~300 notes in ~2 weeks) overwhelmed the topic map structure. The split threshold of 40 was not enforced during ingestion. The condition-based maintenance trigger (">40 notes -> split") was recognized in the last session for representation-learning but not applied systematically.

**Root cause:** Bulk ingestion mode (/learn -> /reduce -> /reflect) prioritizes extraction throughput. Topic map splits require structural analysis that interrupts the extraction flow. The maintenance condition exists but competes with the immediate task.

## Proposals

### Proposal 1: Tiered Review Separation

**Problem:** Master-reviewer bias when run as implementor subagent (Observation #1).

**Change:** Update `/implement` skill to specify review isolation by tier:
- **Tier 3** (critical: VQ-VAE, transformer, detection): Require separate chat session. Implementor writes handoff, reviewer reads cold.
- **Tier 2** (standard: analysis tools, scripts): Current subagent approach is adequate.
- **Tier 1** (trivial: config, docs): Self-review sufficient.

**Validation:** The next Tier 3 implementation should use separate-session review. Compare bug detection rate and fix quality against Phase 8.4 (same-session review).

**Status:** Deferred -- no Tier 3 implementation currently in progress. Record in methodology for next occurrence.

### Proposal 2: Doc Freshness Checks

**Problem:** Stale PROJECTS.md caused agent to distrust correct user claims (Observation #4).

**Change:** Add to CLAUDE.md Common Mistakes to Avoid:
```
- Don't cite documentation status to contradict user claims without verifying CODE first
- When docs contradict user, grep the codebase -- the code is the truth, docs may be stale
```

Also add to ops/reminders.md: after any major feature ships, update PROJECTS.md status.

**Validation:** Self-evident -- the rule prevents a specific observed failure mode.

**Status:** Ready to implement.

### Proposal 3: /reduce Description Self-Check

**Problem:** /reduce produces descriptions that restate titles (Observation #7, recurring 3+ times).

**Change:** Add a mandatory post-extraction description review step to /reduce SKILL.md. After drafting all notes, the skill should:
1. Review each description against the progressive disclosure test
2. Flag any description that starts with the same subject as the title (subject-echo heuristic)
3. Rewrite flagged descriptions to answer "so what?" or "when does this matter?"

This is the lightest intervention from the 6 proposed actions in the observation. If it works, skip the heavier rubric and inline-verify proposals.

**Validation:** Next /reduce batch should have 0 subject-echo descriptions and fewer than 20% title-restatements.

**Status:** Ready to implement.

### Proposal 4: Automatic Inbox Archival After /reduce

**Problem:** Processed inbox files remain in inbox/, inflating counts and wasting ~5 minutes per ghost item (Observation #8, 11 occurrences).

**Change:** Add a step to /reduce: after successful extraction, move the source file to `archive/inbox/`. The source is preserved in the archive for provenance, removed from the active inbox to prevent re-processing.

**Validation:** After implementation, `ls inbox/` should show only genuinely unprocessed files. Session orient hook should report accurate counts.

**Status:** Ready to implement.

### Proposal 5: Contract Pruning Audit

**Problem:** Contract comprehensiveness vs instruction quality (Tension #7), prompt vs boundary enforcement (Tension #9).

**Change:** Audit CLAUDE.md for rules that could move from prompt-level to boundary-level enforcement. Specifically:
1. Schema validation is already boundary-enforced (validate-note.cmd hook) -- remove redundant prompt instructions about schema
2. Session capture is already hook-enforced -- remove redundant prompt instructions about session persistence
3. Identify rules that exist only as prompt instructions and assess: (a) can they become hooks/linters? (b) if not, are they earning their context budget?

**Validation:** Measure CLAUDE.md size before and after. Target: reduce prompt-level rules by 15-20% by moving enforceable rules to hooks and removing redundant rules.

**Status:** Deferred to Phase 5.2 validation (starts 2026-03-06). The audit pairs naturally with the two-week system validation.
