## Why you are doing this

The codebase has **four separate config modules** with overlapping responsibilities, and they **contradict each other** on values that should be identical. Empirical measurements (median ICI, call counts, etc.) are computed on-demand and thrown away, so every new analysis re-derives them. The user asked us to fix both problems. This handoff is the spec.

### Evidence of the contradiction (audited 2026-04-17)

| File | Sample rate | USV freq_min | USV freq_max |
|------|-------------|--------------|--------------|
| `src/usv_spectrogram/config.py` → `SpectrogramConfig` | 250_000 | 30_000 | **125_000** |
| `src/usv_spectrogram/detection/config.py` → `DetectionConfig` | 300_000 | 25_000 | 110_000 |
| `src/usv_spectrogram/detection/extraction_config.py` | (inherits) | 20_000 | 120_000 |
| `usv_language/analysis/config.py` → `AnalysisConfig` | N/A | 20_000 | 120_000 |
| `src/usv_spectrogram/app/core/audio_loader.py` (`AudioLoaderConfig`) | N/A | 0 | 30_000 *(sonic preview only — intentional)* |

**Also note:** `CLAUDE.md` explicitly documents sample rate = 300_000 as the canonical value, but `SpectrogramConfig.expected_sample_rate_hz = 250_000` contradicts it — latent bug that will break the PyQt6 app the first time someone uses `SpectrogramConfig` defaults on a 300 kHz WAV.

### User-specified canonical values (2026-04-17)

- `SAMPLE_RATE_HZ = 300_000`
- `USV_FREQ_MAX_HZ = 120_000` ← user chose this after learning the CNN training set uses 120 kHz
- `USV_FREQ_MIN_HZ = 20_000` ← matches ExtractionConfig (CNN training value); minimizes drift risk
- `N_FFT = 512, HOP = 128` (already consistent in DetectionConfig + ExtractionConfig, matches CLAUDE.md ADR-002)

**Critical constraint — the CNN is frozen at these values.** The production CNN (`models/hard_neg_retrain/best_model.pt`) was trained on 256 px × 20-120 kHz spectrograms generated by `ExtractionConfig`. Changing `freq_min_hz` or `freq_max_hz` in `ExtractionConfig` without retraining produces **silently wrong** inference (same pixel grid, different Hz-per-pixel, features shifted to wrong rows). The user's choice of 20-120 kHz as corpus canonical is precisely to avoid this break: every other module converges ONTO the CNN's values, not away from them.

The PyQt6 app already uses `ExtractionConfig` (20-120 kHz); this is intentional — the human reviewer sees exactly what the CNN sees. Nothing about the app's displayed spectrogram will change visually.

## Layer 1 — Write `src/usv_spectrogram/corpus.py`

New module. Target ~80 lines.

```python
"""Corpus constants — physical facts shared across all USV analysis modules.

Single source of truth for sample rate, USV frequency band, and STFT
parameters. Imported by SpectrogramConfig, DetectionConfig,
ExtractionConfig, AnalysisConfig, and any analysis script that needs
these values. No module should redeclare these.

Values chosen 2026-04-17:
- Sample rate: 300 kHz (matches LMT rig; Nyquist = 150 kHz covers USV band)
- USV band: 20-120 kHz (aligned with CNN training; see constraint below)
- STFT: n_fft=512, hop=128 (matches CLAUDE.md ADR-002 — 586 Hz freq res,
  1.7 ms time res at 300 kHz, 75% overlap)

CRITICAL CONSTRAINT — these values are LOCKED to the production CNN.
The model at models/hard_neg_retrain/best_model.pt was trained on 256-px-tall
spectrograms covering exactly 20-120 kHz. Changing USV_FREQ_MIN_HZ or
USV_FREQ_MAX_HZ here without retraining the CNN produces silently-wrong
inference (same pixel grid, different Hz-per-pixel). If the corpus band
ever needs to change, the CNN must be retrained first.
"""

from __future__ import annotations
from typing import Final

# Physical sample rate of LMT recordings. Enforce this in all pipelines
# (the CLAUDE.md "always specify sr=300000" rule is encoded here).
SAMPLE_RATE_HZ: Final[int] = 300_000

# USV frequency band of interest. Values locked to the CNN training range
# (see docstring). Do NOT change without retraining models/hard_neg_retrain/.
USV_FREQ_MIN_HZ: Final[int] = 20_000
USV_FREQ_MAX_HZ: Final[int] = 120_000

# STFT parameters (see ADR-002).
STFT_N_FFT: Final[int] = 512
STFT_HOP: Final[int] = 128

# Derived values (functions, not constants, so callers see the formula).
def nyquist_hz() -> int:
    return SAMPLE_RATE_HZ // 2

def stft_freq_resolution_hz() -> float:
    return SAMPLE_RATE_HZ / STFT_N_FFT

def stft_time_resolution_ms() -> float:
    return (STFT_N_FFT / SAMPLE_RATE_HZ) * 1000.0

def stft_hop_ms() -> float:
    return (STFT_HOP / SAMPLE_RATE_HZ) * 1000.0
```

Update the four config files to import from `corpus`:

### `src/usv_spectrogram/config.py`
- `expected_sample_rate_hz: int = 250_000` → `SAMPLE_RATE_HZ` *(value change: 250k→300k — fixes long-standing latent bug vs CLAUDE.md ADR-001)*
- `f_min_hz: float = 30_000.0` → `float(USV_FREQ_MIN_HZ)` *(value change: 30k→20k)*
- `f_max_hz: float = 125_000.0` → `float(USV_FREQ_MAX_HZ)` *(value change: 125k→120k — aligns with CNN)*
- Note: `window_length = 2048` is a spectrogram-specific param (not corpus-level) — leave as-is

### `src/usv_spectrogram/detection/config.py`
- `sample_rate: int = 300_000` → `SAMPLE_RATE_HZ` *(no value change)*
- `freq_min_hz: int = 25_000` → `USV_FREQ_MIN_HZ` *(value change: 25k→20k — widens the detection band to match extraction; may require retuning `energy_threshold_db` — see "Retuning check" below)*
- `freq_max_hz: int = 110_000` → `USV_FREQ_MAX_HZ` *(value change: 110k→120k — same caveat)*
- `n_fft: int = 512` → `STFT_N_FFT` *(no value change)*
- `hop_length: int = 128` → `STFT_HOP` *(no value change)*

**Retuning check for DetectionConfig:** widening the band from 85 kHz (25-110) to 100 kHz (20-120) changes the total energy in the band by ~18%. The default `energy_threshold_db = -60.0` is relative to max energy in the band (see `detection/config.py:39` comment), so the impact should be small. **Verify by running `scripts/run_batch_detection.py` on one known-good WAV and diffing the detection count vs the pre-refactor baseline.** If detection count drops/rises by >5%, retune the threshold (out of scope for this handoff — flag to user).

### `src/usv_spectrogram/detection/extraction_config.py` — **DO NOT CHANGE VALUES**
- `freq_min_hz: int = 20_000` — already matches corpus; leave the literal for safety
- `freq_max_hz: int = 120_000` — already matches corpus; leave the literal for safety
- **Rationale:** this config is frozen at CNN training values. If corpus.py ever changes (future work), ExtractionConfig must NOT automatically track it — that would silently break the model. Recommended approach: add a comment at the top of the file:
  ```
  # NOTE: freq_min_hz/freq_max_hz are INTENTIONALLY hardcoded here (not imported
  # from corpus.py). These values define the pixel grid of every CNN training
  # image in models/hard_neg_retrain/. Changing them without retraining will
  # silently corrupt inference. If corpus values ever diverge from (20_000, 120_000),
  # that's a decision point that requires retraining the CNN.
  ```
  Also add an assertion at module import time that the current values equal the current corpus values (so a future corpus change is caught immediately):
  ```python
  from ..corpus import USV_FREQ_MIN_HZ, USV_FREQ_MAX_HZ
  assert ExtractionConfig.__dataclass_fields__["freq_min_hz"].default == USV_FREQ_MIN_HZ, (
      "ExtractionConfig freq_min_hz drifted from corpus. If corpus changed, retrain CNN."
  )
  assert ExtractionConfig.__dataclass_fields__["freq_max_hz"].default == USV_FREQ_MAX_HZ, (
      "ExtractionConfig freq_max_hz drifted from corpus. If corpus changed, retrain CNN."
  )
  ```

### `usv_language/analysis/config.py` (AnalysisConfig)
- `freq_min_hz: int = 20_000` → `USV_FREQ_MIN_HZ` *(no value change)*
- `freq_max_hz: int = 120_000` → `USV_FREQ_MAX_HZ` *(no value change)*

### `src/usv_spectrogram/app/core/audio_loader.py` — **DO NOT CHANGE**
This is a sonic-only preview component (`freq_max_hz = 30_000`). It's intentionally not USV-band — leave it alone. Document this exception in a comment referencing `corpus.py` so future readers don't "fix" it.

## Context from this session (2026-04-17)

The user asked this question while deep in the Phase 17 SIS benchmark. Triggering event: the SIS driver computed Scattoni-7 MI = 0.076 bits, but Phase A2 had reported 0.092 bits. Investigating the discrepancy revealed:
1. Phase A2 uses bout-aware MI (exclusion of cross-bout pairs)
2. Phase A2's 0.6s bout threshold = `3 × median(IOI)`, a heuristic, NOT a rigorous valley-finder
3. Phase A1's `detect_bouts` doesn't respect file boundaries → 829 cross-file pairs (10% of all pairs) were injected as fake long ICIs
4. Mickey cited literature: 10 ms intra-call, 90 ms within-bout median silent gap, 250-500 ms between-bout convention
5. Our audit confirmed: median silent gap IS 87 ms (matches literature), median IOI IS 193 ms
6. **The empirical audit revealed that none of these numbers are stored anywhere reusable** — which prompted this handoff

The `src/usv_spectrogram/classification/sis_baselines.py` implementation of Phase 17 module 17.1 is now the reference for the "every analysis prints its parameters" pattern — see its `_print_parameters()` and `_write_parameters_json()`. `audit_corpus.py` should follow the same pattern.
