# CNN Training Data Window Size — Provenance Report

**Date:** 2026-03-25
**Investigation:** What window size trained `models/production/best_model.pt`?

## Summary

The production CNN was trained on **variable-width windows (105–270ms for positives, 128px/64ms for negatives)** from `data/full_training_dataset/`. At inference time, the app's sliding window feeds **42.7ms (100px) patches zero-padded to 512px**. The model works despite this mismatch because zero-padding during both training and inference creates a structurally similar input, but probability compression (max ~0.58) indicates the model is underperforming due to the domain shift.

### 3. Window Sizes in Training Data

#### Positive samples (USVs) — from `spectrograms_training/`

Generated by `SpectrogramExtractor` from detection candidates. `Candidate.create()` applies **50ms context before + 50ms context after** the detection boundaries (defaults at `candidate.py:58-59`). The `_render_training` method then resizes to `pixels_per_ms=2.0`, clamped to [128, 512] pixels.

Actual values from `candidates.csv`:

| USV duration | + Context (100ms) | Total window | Image width |
|-------------|-------------------|-------------|-------------|
| 5ms | 105ms | 105ms | 210px |
| 20ms | 120ms | 120ms | 240px |
| 35ms | 135ms | 135ms | 270px |

**Positive training images are 210–270px wide (105–135ms).**

#### Negative samples — comprehensive negatives

`scripts/generate_comprehensive_negatives.py` uses `--duration-ms=40.0` (default at line 581) and `context_before_ms=0.0, context_after_ms=0.0` (lines 185-186). A 40ms sample produces 80px raw, clamped to `min_width_px=128`.

**Comprehensive negative training images are 128px wide (representing 40ms of audio, rendered at 2px/ms but clamped to minimum).**

#### Original negatives — from `spectrograms_training/`

Same extraction pipeline as positives. Variable width with 50ms+50ms context. Approximately 120–240px.

### 4. Training-Time Padding

`data_loader.py:pad_collate_fn` (line 124) pads all images in each batch to the maximum width in that batch. With batch_size=32 and images ranging 128–512px, most batches contained at least one wide image, so shorter images (especially the 128px negatives) were heavily zero-padded during training.

### 5. Inference-Time Behavior

`SlidingInference` (`sliding_inference.py:37-41`):
- `window_width_px=100` → extracts 100 STFT columns
- Each column = 1 hop = 128 samples / 300,000 Hz = **0.4267ms**
- 100 columns = **42.67ms**

`_prepare_batch` (lines 312-322) then **pads to 512px**:

```python
MAX_WIDTH = 512
batch_tensor = torch.nn.functional.pad(batch_tensor, (0, pad_width, 0, 0), value=0)
```

So the CNN receives: 100px of content + 412px of zeros = 512px total.

### 6. Why It Works (Partially)

The CNN architecture uses `nn.AdaptiveAvgPool2d((1, 1))` — global average pooling that reduces any spatial size to 1×1. The zero-padded region contributes near-zero activations after ReLU, so the model focuses on the content portion.

During training, the 1000 comprehensive negatives (54% of training data) were 128px of content zero-padded to ~400–512px. This is structurally similar to the inference-time input (100px of content zero-padded to 512px). So the CNN learned to classify "small content region + large zero region" inputs.

### 7. Why It Doesn't Work Well

| Symptom | Likely cause |
|---------|-------------|
| Probability compression (max ~0.58) | Positive training images (210–270px) look very different from inference windows (100px). The model never saw a USV in only 100px of content. |
| Required threshold of 0.05–0.25 | Consequence of probability compression — model is never confident. |
| Per-window normalization sensitivity | Training normalization was per-image on larger windows; inference normalization on 42.7ms windows amplifies noise differently. |

## The Dataset Assembler (Not Used for This Model)

`DatasetAssembler` (`assembler.py`) with `jitter_window_ms=40.0` + `jitter_context_padding_ms=20.0` = 80ms total was implemented at `2fa9ad4c` (2026-02-21) — **19 days after** the production model was trained. `run_training_cycle.py` uses it, but no training cycle has produced a model that replaced `models/production/best_model.pt`.

## Recommendation

Retrain with the `DatasetAssembler` pipeline (`run_training_cycle.py`) to produce training images that match the inference window. The assembler's 40ms jitter window + 20ms padding = 80ms total (160px at 2px/ms) is much closer to the inference window (100px ≈ 42.7ms), though still not an exact match.

For best results, the training window should match inference exactly:
- **Option A:** Train on ~42.7ms windows (100 STFT columns rendered as images) to match `SlidingInference`
- **Option B:** Change `SlidingInference.window_width_px` to match training image widths
- **Option C:** Use the assembler's 80ms windows and update `SlidingInference` to use ~188px windows (80ms / 0.4267ms per column)

Any option should eliminate the probability compression and allow using a normal threshold (~0.5).
