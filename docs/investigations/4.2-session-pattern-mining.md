### Transcript Format

JSONL files with one JSON object per line. Each line includes:
- `type`: "user", "assistant", "progress" (tool calls), "file-history-snapshot"
- `message.content`: Full message text/tool calls
- `timestamp`, `sessionId`, `version`, `gitBranch`
- Tool call results, hook progress events
- Full thinking traces (encrypted signatures)

**Extractable patterns:**
- Failed searches (tool calls returning empty results)
- Repeated context gathering (same file read multiple times)
- Correction patterns ("no, don't...", "instead...")
- Query reformulations (search → different search)

### Key Design Question

**Is batch mining architecturally viable given transcript ephemerality?**

**No.** With a ~3-day retention window (only transcripts from Mar 19-22 survive), any batch mining approach runs after the data is already gone. By the time a user runs `/remember --mine-sessions`, the most valuable transcripts (older sessions with correction patterns) have been GC'd.

## Feasibility Assessment

### Option A: Capture-Time Extraction (in session-capture.ps1)

Enrich the session JSON pointer at session end with extracted patterns. The session-capture hook already creates session pointers — it could also scan the still-live transcript for:
1. User corrections/feedback (messages containing "no", "don't", "instead", "that's wrong")
2. Search patterns (tool calls to qmd/Grep that returned 0 results)
3. Repeated file reads (same file read 3+ times in one session)

**Pros:** Data captured before GC; lightweight; builds on existing hook
**Cons:** Adds latency to session end; heuristic extraction may miss subtle patterns; only captures within single session (can't find cross-session patterns)

### Option B: Batch Mining (current /remember architecture)

Mine surviving transcripts in bulk.

**Pros:** Can find cross-session patterns; richer analysis possible
**Cons:** Only 13 of 347 sessions survive; most valuable data already gone; architecturally wrong

### Option C: Hybrid — Lightweight capture + periodic synthesis

Session-capture extracts signals (corrections, failed searches) into `ops/sessions/signals/`. A periodic skill synthesizes signals into methodology notes when patterns accumulate (3+ similar signals).

**Pros:** Captures everything before GC; enables cross-session pattern detection; separates extraction from synthesis
**Cons:** Most complex; requires two new components

## Recommendation

**Option C (hybrid) is the right architecture, but not worth building now.** Here's why:

1. The primary friction source (session-orient failing) has a much simpler fix (4.1 qmd shim repair)
2. The /remember skill is now functional for manual pattern capture
3. The 13 surviving transcripts don't contain enough correction patterns to justify building extraction infrastructure
4. Building capture-time extraction adds latency to every session end for uncertain benefit

**Deferred action:** If the user notices recurring correction patterns that /remember doesn't catch, revisit Option C. The architecture is sound but premature.

### What to do with the 13 surviving transcripts

A quick manual scan would be more efficient than building tooling:
- Scan 2-3 transcripts for correction patterns
- If any are found, capture them manually with `/remember`
- Not worth automating for 13 files

## Decision

**Session mining deferred.** The transcript ephemerality problem is real but the ROI of building extraction infrastructure doesn't justify the effort given that:
1. Knowledge activation was never working (4.1) — fix that first
2. Manual /remember works for explicit corrections
3. The 13 surviving transcripts are too recent to contain accumulated patterns
